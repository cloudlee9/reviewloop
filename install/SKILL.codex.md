# rloop —— 你驱动这个循环

## 分工

**`rloop`（app）没有上下文，只干机械活**：起一个无头、无状态的 reviewer 子进程（默认放开到能跑测试，但绝不改用户的代码——跑完核对工作区指纹，动过会记进本轮报告 —— 注意你这边的 reviewer 是 claude，它没有可供核查的执行事件流，所以不会自动作废；`--no-verify` 关回只读），算 diff 范围，管账本，出结构化 findings，展示面板。**它从不改用户的代码，也不做循环。**

**你（这个会话）有上下文** —— 知道这些代码为什么写成现在这样、之前讨论过什么、哪些是刚改的。所以循环由你驱动，findings 由你处理，回应由你写。

两边通过**文件**交接，不是 API：

```
app 写 →  round-NN/review.json   结构化结果（门禁校验用）
          round-NN/review.md     同一份内容的人类可读版（**每轮把链接贴给用户**）
          round-NN/diff.patch    这轮送审了什么
             ↓
你 读 →   改代码
             ↓
你 写 →   round-NN/response.md   逐条交代
             ↓
app 读 →  下一轮喂给 reviewer 逐条裁决
```

## 循环怎么跑

**跑起来就一直跑，不要每轮停下来问用户。** 只有下面「什么时候停下来问」里列的情况才中断。

### 1. 审一轮

```bash
rloop --json
```

前台阻塞，几分钟。stdout 是一个 JSON 对象。退出码就是判定：

| 码 | 含义 | 你该做什么 |
|---|---|---|
| 0 | 达标 | 停，汇报走势和结论 |
| 2 | 未达标 | 看 `can_continue`，见下 |
| 3 | reviewer 自相矛盾 | **不要**当成达标，停下来问用户 |
| 1 | 出错 | 读 stderr 如实报告，不要重试掩盖 |

`--json` 里 `outcome` 是 `deadlocked` 时：某条 finding 连续几轮判 `not_fixed` 而你每轮都有实质回应 —— 双方顶住了，rloop 提前收场。**这不是放行**，判定仍是未达标。别再起新一轮（起了也不会收敛），把那几条连同双方的理由一起交给用户拍板。

**退出码 2 不等于还能继续**：跑满轮数、连续两轮无进展熔断，退出码同样是 2。载荷里这两个字段才准：

- `can_continue: false` → **停止循环**，把走势和遗留 findings 交给用户
- `fix_allowed: false` → 范围钉在历史提交上，你改工作区也进不了送审 diff，**只出报告别动手**

首次跑新建 loop；再跑自动接在同一个 loop 上、轮次递增。`--new` 或带 `--base`/`--commit`/侧重点会另起。

### 2. 逐条处理 findings

对每一条**独立判断**：

- **同意** → 改。修根因不是压症状。critical / high 优先
- **不同意** → 不改，写明理由。有证据的反驳是合法结果，下一轮可能被判 `rebutted_and_accepted`

**只改 findings 点到的地方。** 不要顺手重构、不要按自己口味改写、不要"既然改到这里了就一起优化"。代码是用户的。

改完跑一遍项目自己的验证（测试 / build / lint），修掉你弄坏的。

### 3. 写回应

写进 `round-NN/response.md`，**每条 finding 都要有，一条都不能漏**：

```markdown
## [HIGH] F1 <一句话说清是哪条>
**采纳。** 怎么改的、改在哪些文件、配了什么回归用例。

## [MEDIUM] F2 <…>
**反驳。** 为什么不成立或不适用，证据是什么（复现、命令输出、代码行号）。
```

下一轮 reviewer 会读它，并在 `prior_findings_status` 里对每条给出 `fixed` / `partially_fixed` / `not_fixed` / `rebutted_and_accepted`。**写得含糊就会被判 `not_fixed`。不写等于什么都没做，会掉分。**

### 4. 回到第 1 步

直接再跑，不用问用户。

## 什么时候停下来问用户

- 退出码 3（reviewer 自相矛盾）
- `can_continue: false`（熔断或跑满轮数）
- 你和 reviewer 在**同一条 finding** 上反复拉锯两轮以上
- finding 要求的改动明显超出用户原本的意图（比如要你重构一个根本没动过的模块）
- 你想反驳，但拿不出证据

**除此之外自己往下跑。** 用户说"审一下"意思是审到不能再审为止，不是审一轮回来请示。

## 汇报什么

**每一轮都要说，不是等循环跑完才说。** 一轮要跑几分钟，用户盯着终端，中间只有一句
「6.5 / 4.0 / 2 个阻塞项」的话，他不知道发生了什么、也不知道你接下来要动什么。

rloop 自己会把完整结果打在终端上（`--json` 时走 stderr）：findings、上一轮的裁决、
它实际跑了什么。**所以别复述那份内容**——用户已经看到了。你要补的是它给不了的那半：

每轮改完，用一小段说清楚：

- **每条 finding 你怎么处理的**：采纳了怎么改的（哪个文件、什么思路）、反驳了理由是什么
- **你不同意但照做了、或者干脆没做的**——这项最要紧，用户需要知道哪里有分歧
- 下一轮打算让它重点看什么（如果你调整了侧重点）

循环整个结束时再给一次总的：走势、每条 finding 的最终去向、遗留了什么。

不要复述 reviewer 的原话充数，也不要只说「已修复 3 个问题」——那等于没说。

### 每轮都要留下两个可点的链接

**这轮改完、下一轮起之前**，把这两个文件贴出来：

```
本轮详情：.review-loops/<loop-id>/round-03/review.md
我的回应：.review-loops/<loop-id>/round-03/response.md
```

写成 markdown 链接（`[round-03/review.md](.review-loops/xxx/round-03/review.md)`），
用**相对项目根目录**的路径 —— 终端里能直接点开。前者的绝对路径在 `--json` 载荷的
`review_md_path` 里（这一轮没成的话是 `null`，那就别贴），后者是 `response_path`。

**时机就是全部意义所在。** 下一轮 `rloop` 是前台阻塞的，一跑几分钟到十几分钟，
那段时间你不会输出任何东西 —— 用户干等着。他手里得有东西可读，而那东西只能是
**上一轮**留下的。等循环整个跑完再一起给，等于让他先干等半小时再补看。

`review.md` 是 rloop 渲染的完整版：走势表、小结、每条 finding 带 `file:line` 和
建议、reviewer 实际跑了哪些命令。**你不用把这些复述一遍**，贴链接就够了 ——
你自己那段话只讲它给不了的：你怎么处理的、哪里不同意。

## 面板

用户想自己看的时候：

```bash
rloop web     # 网页面板：走势图、findings 折叠、diff 高亮、实时进度
```

面板是**观察者**：能看能审一轮，但**没有「处理」按钮**——按下去的必然是个没上下文的陌生会话，那正是这套东西刻意避开的。处理永远在你这里。

## 常用参数

```bash
R="--reviewer claude"              # 下面每条都带着它

rloop --json $R                   # 审当前改动（脏工作区→未提交；干净→相对主干；再没有→最后一个 commit）
rloop --json $R --base main       # 相对 main 的全部改动
rloop --json $R --commit HEAD~2   # 某个 commit 引入的改动（fix_allowed 会是 false）
rloop --json $R 重点看并发安全     # 给 reviewer 一个侧重点
rloop --json $R --effort xhigh    # 拉高推理档位，贵但挖得深很多
rloop --json $R --new             # 强制开新 loop
rloop --json $R --label "GUI 切分" # 给这个 loop 起个名字，列表里好认
rloop --json $R --no-verify        # 把 reviewer 关回只读：审来路不明的代码时用，代价是它拿不到实证
rloop status / report / replay N  # 走势 / 报告 / 回看第 N 轮的完整输入（不用带 $R）
```

**每次调用都带 `--reviewer claude`。** 你就是 codex，rloop 默认也用 codex 审 ——
不指定的话就是自己审自己，独立意见无从谈起。同一台机器上 Claude 那边的 rloop
仍然用 codex 审，所以这件事不能靠全局配置，只能每次显式写。

## 你自己就是被审的那个人

代码很可能是你上一轮刚写的。你会本能地觉得 reviewer 小题大做，或者急着证明自己没错。

对抗办法只有一个：**要求自己拿证据**。想反驳就去复现、去跑命令、去引代码行号。拿不出证据的反驳不写，直接改。

反过来也一样——reviewer 说的不一定对，它提过前提就不成立的 finding。照单全收和据理力争都不是目标，判断才是。

有一类错误尤其要防：**声称改了但实际没改**。用脚本做文本替换时目标串可能已经过时、`str.replace` 静默失败，于是测试全绿、回应写得斩钉截铁、功能是空的。改完务必用 grep 或 Read 确认那段代码真的在。
